# Zenodo deposit: CaliciTyper reference data

This folder is gitignored. It stages a Zenodo **Dataset** deposit. Upload its
contents, then put the resulting URL and DOI into
`calicityper/data/reference_manifest.json` (`download_url`, `doi`) and commit.

## Status 2026-11-18: staged at 0.8.1, NOT uploaded — and now optional

What changed since the 0.7.0 staging: **the reference set is already published
and resolvable.** The v0.8.0 release on GitHub, tagged `reference-0.8.0`,
carries `calicityper-reference-0.8.0.tar.gz`, and the manifest's `download_url`
points at it. `calicityper setup` downloads and verifies from there, and CI
exercises that same path with no override. Hosting is therefore solved.

A Zenodo deposit is no longer needed to make the tool work. What it would
still provide is a **citable, persistent DOI** that does not depend on a GitHub
release staying put — which reviewers of the manuscript asked for explicitly.
That is the only remaining reason to upload.

**The `doi` field is wrong either way right now.** It still reads
`10.5281/zenodo.24161236`, the 0.6.1 deposit: a superseded dataset. Either
deposit 0.8.1 and update it, or clear the field. Leaving it pointing at 0.6.1
while `download_url` serves 0.8.0 (and 0.8.1 is not released yet) is the worst of the three.

## Contents

| File | Size | What it is |
|---|---|---|
| `calicityper-reference-0.8.1.tar.gz` | 1.9 MB | the reference set: BLAST database, and the norovirus **and sapovirus** VP1/RdRp alignments, `.orf` and annotation files. This is what `calicityper setup` downloads. 229 artefacts. |
| `reference_manifest.json` | 20 kB | checksum manifest for the above; `setup` refuses any set that does not match it |
| `reference_accessions.tsv` | 16 kB | accession list for the reference set |
| `recombination-datasets-0.8.0.tar.gz` | 97 kB | the nine synthetic recombination alignments with `truth.json` giving each planted breakpoint, and a README. Two carry no planted breakpoint and are the negative controls. |
| `SHA256SUMS` | — | checksums of the two tarballs |

**Version:** `0.8.1` — must match `reference_set_version` in the manifest.

### Why 0.8.1 and not 0.8.0

The 0.8.0 archive, which is the one currently published on GitHub, carries
three stale files: `reference_sequences_sapovirus_VP1/GNA4.{orf,fasta,aln}`,
left behind when MH003837 was relabelled GNA4 to GXV. The builder wrote one
file per genogroup and never removed a genogroup that had lost its last
member, so the per-genogroup files held 51 VP1 types where the pooled
`all.orf` held 50. No call is affected — the genogroup BLAST database has no
GNA4 entry and the reference set is chosen by genogroup name, so nothing can
reach them — but they are checksummed as correct by a manifest whose purpose
is exactness, and they assert a genotype the taxonomy retracts. A reference
set whose content changes must take a new version, which is why this is 0.8.1
rather than a quiet replacement of the 0.8.0 asset.

### What happened to the two 0.6.1 archives

**`recombination-datasets-0.6.1.tar.gz` was rebuilt as 0.8.0.** Its nine
alignments are generated deterministically by `tests/synthetic.py` from fixed
seeds, and regenerating them at 0.8.0 reproduces the 0.6.1 files byte for
byte. Only the label changed, so that it does not imply the data is stale.

**`benchmark-datasets-0.6.1.tar.gz` was deleted and has now been replaced**
by `benchmarking-datasets-0.8.1.tar.gz`, rebuilt from the current `results/`
by a script rather than by hand, and with the comparator's raw calls excluded
by construction (the builder re-opens the finished archive and fails if it
finds them). The 0.6.1 archive was dropped for two reasons. Its
derived tables are superseded by `analysis/benchmark_outputs/` in the
repository, which is current and carries a README mapping every claim in the
paper to the file that produced it; and its runtime tables predate the peak
memory measurement. More importantly, it contained `rivm_calls.csv`, the
Norovirus Typing Tool's own output for all 5,986 sequences, which
`validation/README.md` states is **not redistributed** by this project.
Uploading it would have published exactly the data the repository
deliberately withholds. If a benchmark archive is wanted in the deposit,
rebuild it from `analysis/benchmark_outputs/` and leave the comparator's raw
calls out.

## The benchmark outputs are staged elsewhere

`benchmarking-datasets-<version>.tar.gz` is no longer staged here. It is
produced by the benchmarking repository, from data that repository owns, and
is staged in `calicityper_runs/zenodo/` beside its own `SHA256SUMS`. This
folder holds only what the tool itself produces: the reference set, the
synthetic recombination datasets generated by `tests/synthetic.py`, and the
manifest and accession list that describe them.

Upload them to the same Zenodo deposit if you want one DOI for everything, or
to two deposits if you would rather the reference set and the benchmarks be
citable separately — which is the better fit, since a benchmark rerun does
not change the reference set and should not force a new version of it.

## Uploading

1. Create the deposit as a **Dataset**, not Software.
2. Upload every file in this folder.
3. Either copy the Zenodo file URL for the reference tarball into
   `download_url`, or leave it on the GitHub asset, which already works, and
   use Zenodo only for the DOI.
4. Copy the **version** DOI, not the concept DOI, into `doi`: a run should
   record the exact dataset it used, not a moving pointer.
5. Rebuild the manifest so the recorded values are the ones shipped:

       python scripts/build_reference_manifest.py --download-url <url> --apply

   The flag HEAD-checks the URL and refuses to write if it does not resolve.
6. Commit the manifest and put the DOI in the manuscript's Data Summary.
